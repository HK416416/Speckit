## 三、分特性分析

### 3.1 单模型实验：TPOT 与吞吐量高度一致

以下 4 组实验（主基线 + 前缀缓存 + 分块预填充 + 并发度 8/64）均不涉及投机推理，**仅 1 个模型驻留显存**：

| 实验 | TPOT | 吞吐 | 与主基线的 TPOT 偏差 |
|------|:---:|:---:|:---:|
| 主基线 | 17.9ms | 54.39 | — |
| 前缀缓存 | 17.8ms | 54.68 | -0.6% |
| 分块预填充 | 17.9ms | 54.57 | ±0% |
| seqs=8 | 17.9ms | 54.23 | ±0% |
| seqs=64 | 17.9ms | 54.60 | ±0% |
| 专属基线 (seqs=4) | 17.9ms | 54.09 | ±0% |

```text
TPOT 波动范围: 17.84 ~ 17.89 ms  (±0.3%)
吞吐波动范围: 54.09 ~ 54.68 tok/s  (±0.5%)
```

**结论**：单模型场景下 TPOT 与吞吐量完全受 TPOT 主导（KV Cache 管理使 decode 性能高度一致）。任何单模型 TPOT 偏差 <1%，属于测量噪声。说明 **vLLM 的 KV Cache 管理非常稳定**。

### 3.2 投机推理：TPOT 暴涨 4.7×，吞吐暴跌 4.7×

| 指标 | 投机解码专属基线 | 投机推理 | 变化 |
|------|:---:|:---:|:---:|
| TTFT avg | 62.4ms | 131.0ms | ↑ 2.1× |
| TTFT P50 | 49.9ms | 108.2ms | ↑ 2.2× |
| TTFT P95 | 119.0ms | 206.4ms | ↑ 1.7× |
| **TPOT avg** | **17.9ms** | **84.2ms** | ↑ **4.7×** |
| **吞吐量** | **54.1 tok/s** | **11.5 tok/s** | ↓ **4.7×** |

> 两组参数完全一致（max-len=1024, gpu=0.80, seqs=4, enforce-eager, compilation=NONE），**唯一变量**：是否启用 `--speculative-config`。

**根因**：draft model (0.5B) 在 RTX 4050 上的单步耗时与 target (1.5B) 之比 c ≈ 0.43——远大于 Leviathan 论文的 c < 0.05。双模型加载还导致额外显存压力。投机推理不仅未加速，反而显著变慢。

### 3.3 前缀缓存：TTFT 降低 15.7%

| 指标 | 主基线 | 前缀缓存 | 变化 |
|------|:---:|:---:|:---:|
| TTFT avg | 51.1ms | **43.1ms** | ↓ 15.7% |
| TTFT P50 | 43.2ms | **33.8ms** | ↓ 21.8% |
| TPOT | 17.9ms | 17.8ms | 不变 |
| 吞吐 | 54.39 | 54.68 | 不变 |

**生效机制**：前缀缓存复用共享前缀的 KV Cache。10 个请求中有部分共享相同开头（如"请解释"），这些请求的 prefill 阶段被跳过。

**注意**：本次测试 Prompt 集中共享前缀的比例有限（仅部分"请解释"开头）。如果使用刻意设计的大比例共享前缀数据集（如 ShareGPT 多轮对话），TTFT 降低幅度会更显著。

### 3.4 分块预填充：TTFT 降低 11.0%

| 指标 | 主基线 | 分块预填充 | 变化 |
|------|:---:|:---:|:---:|
| TTFT avg | 51.1ms | **45.5ms** | ↓ 11.0% |
| TTFT P50 | 43.2ms | 36.9ms | ↓ 14.6% |
| TPOT | 17.9ms | 17.9ms | 不变 |
| 吞吐 | 54.39 | 54.57 | 不变 |

**生效机制**：长 prompt 的 prefill 被切为多块，GPU 在处理短块时可以有更高的利用率。对单并发低负载场景效果中等，多并发混合长度 prompt 时效果更显著。

### 3.5 并发度梯度：8 → 16 → 64

| 实验 | seqs | TTFT avg | TTFT P50 | TTFT P95 | 吞吐 |
|------|:---:|:---:|:---:|:---:|:---:|
| 低并发 | 8 | 56.5ms | 49.1ms | 125.1ms | 54.23 |
| **主基线** | **16** | 51.1ms | 43.2ms | 74.9ms | 54.39 |
| 高并发 | 64 | **44.4ms** | 38.1ms | 76.4ms | 54.60 |

```text
seqs 8  → 16: TTFT ↓ 9.6%,  吞吐 ↑ 0.3%
seqs 16 → 64: TTFT ↓ 13.1%,  吞吐 ↑ 0.4%

趋势: TTFT 随 seqs 增加而降低，吞吐量几乎不变
```

**解读**：

- **seqs=8**：10 个请求有轻微排队（8 槽 → 10 请求），TTFT 略高
- **seqs=16**：恰好容纳 10 个请求（16 槽），无排队，TTFT 改善
- **seqs=64**：远大于 10 个请求（64 槽），饱和冗余，TTFT 进一步略降

**关键发现**：在单并发低负载（10 个请求串行）场景下，**`max-num-seqs` 的对 TPOT 和吞吐量的影响极小**（<1%）。TTFT 的小幅差异（~13ms）主要来自 vLLM 内部调度开销，而非真正的并发竞争。并发度的效果在多请求并发场景下才会显著体现。

### 3.6 全特性组合

| 指标 | 专属基线 | 全特性组合 | 变化 |
|------|:---:|:---:|:---:|
| TTFT | 62.4ms | 131.0ms | ↑ 2.1× |
| TPOT | 17.9ms | 83.3ms | ↑ 4.7× |
| 吞吐 | 54.1 | 11.6 tok/s | ↓ 4.7× |

**结果与投机推理几乎完全一致**（TPOT 83.3 vs 84.2ms, TTFT 131.0 vs 131.0ms）——说明投机推理是主导因素，前缀缓存和分块预填充在双模型场景下被投机推理的瓶颈完全掩盖。

## 四、核心结论

### 结论 1：端侧 TPOT 在单模型下高度稳定（~17.9ms）

所有单模型实验的 TPOT 偏差 < 0.3%，吞吐偏差 < 0.5%。vLLM 的 V1 引擎（即使禁用了 CUDA Graph 和 torch.compile）在 RTX 4050 上对 Qwen2.5-1.5B 的 decode 管理非常稳定。

### 结论 2：端侧投机推理失效，减速 4.7×

```
draft (0.5B) 单步耗时 / target (1.5B) 单步耗时 = c ≈ 0.43
Leviathan 论文 c < 0.05 → 加速 2-3.4×
端侧实测 c ≈ 0.43 → 减速 4.7×
```

**定量证据**：单模型 TPOT = 17.9ms，投机推理 TPOT = 84.2ms。draft model 的串行开销吞噬了所有理论收益。

### 结论 3：前缀缓存是端侧最有效的单特性优化

TTFT 降低 **15.7%**（51.1 → 43.1ms），TPOT 无影响。代价仅为少量 KV Cache 复用开销，完全不增加显存压力。**建议在所有端侧部署中默认开启**。

### 结论 4：分块预填充有正向但有限的收益

TTFT 降低 **11.0%**（51.1 → 45.5ms），在单并发低负载场景下效果中等。多并发 + 混合长度 prompt 时效果会更好。

### 结论 5：单并发低负载下并发度影响极小

TPOT 和吞吐量不受 `max-num-seqs` 影响（<1%），TTFT 小幅波动（8ms 量级）。当前实验串行 10 个请求无法触发真正的并发竞争。

### 结论 6：投机推理是双模型场景的唯一瓶颈

全特性组合与纯投机推理的性能**几乎完全相同**——说明在双模型场景下，前缀缓存和分块预填充的效果被投机推理的巨大开销完全覆盖。

## 八、论文对照分析

### 8.1 Leviathan (ICML 2023) — 投机推理奠基论文

| 论文内容 | 本实验对应 | 对照结果 |
|----------|-----------|----------|
| draft-verify + rejection sampling 无损性 | `hf_server.py` 投机推理模式 | ✅ 算法直接实现 |
| 加速比公式 `(1-α^(γ+1))/((1-α)(γc+1))` | 端侧实测代入 | c=0.43 → 理论加速比 0.95×（减速），实测 4.7× 减速 |
| α = 0.62-0.88 (T5-Small vs T5-XXL) | Qwen 0.5B vs 1.5B | 端侧 α 未经独立测量，但估计偏低 |
| c < 0.05 (draft 耗时可忽略) | 端侧 c ≈ 0.43 | **端侧 c 值高出 8.6×，是投机推理失效的根本原因** |
| 最优 γ 由 α 和 c 决定 | k=3 的选择 | 在 c=0.43 下，γ 增大反而加速恶化（γc+1 分母放大） |
| approximation model 比 target 小 2 个数量级 | 端侧 0.5B vs 1.5B = 3× | **尺寸差远远不够**——论文要求 ~100× 以上 |

**核心对照**：Leviathan 论文的加速比公式完美预测了端侧投机推理的失效。当 `c → 0`（论文云侧条件），投机推理加速 2-3.4×；当 `c ≈ 0.43`（本实验端侧），投机推理减速 4.7×。实验数据直接验证了论文理论——公式中 `γc+1` 分母放大是端侧失效的数学原因。

### 8.2 SpecInfer (ASPLOS 2024) — 树形投机推理

| 论文内容 | 本实验对应 | 对照结果 |
|----------|-----------|----------|
| Token Tree 验证成功率 57% → 97% (top-5) | vLLM 投机推理仅用 k=3 线性序列 | 未使用树形 draft——如果使用 top-3 候选树，接受率有望提升 |
| topology-aware causal mask 并行验证 | 实验因 CUDA 13 冲突关闭 flashinfer | 树形验证需要自定义 attention mask，在 vLLM V1 引擎下不可用 |
| 多 SSM collective boost-tuning | 本实验仅 1 个 draft model | 论文的多 SSM 方案需额外 GPU |
| token tree 宽度增加验证成功率 | 未测试 | 若能实现 top-3 tree（而非 k=3 线性），接受长度有望提升 |
| 树形 vs 序列延迟对比：1.2-1.5× 额外提升 | 未测试 | 本实验已证明有空间——树形 draft 是端侧提升方向之一 |

**核心对照**：本实验投机推理使用 **线性序列**（Leviathan 原始方案），而非 SpecInfer 的**树形结构**。SpectInfer 论文表明 top-5 树形可将验证成功率从 57% 提升到 97%。端侧如果实现 simplified top-3 tree（在 RTX 4050 上可行），接受长度有望翻倍，部分弥补 c 值过高的损失。这是**端侧投机推理的后续优化方向**——不需要更小的 draft model，而是让 draft model 生成更聪明的候选结构。

**与 myDraft_Verify 的关联**：`core/draft.py` 中的 `_draft_tree()` 方法已实现 SpecInfer 的 expansion-based 树形 draft，可在自主实践中对比树形 vs 线性在端侧的接受率差异。

### 8.3 EAGLE-2 (2024) — 动态 Draft Tree

| 论文内容 | 本实验对应 | 对照结果 |
|----------|-----------|----------|
| confidence ≈ acceptance rate (强正相关) | vLLM 投机推理未暴露接受率/confidence 数据 | 无法直接验证——vLLM 黑盒不提供每步 confidence |
| 动态 draft tree 比静态树 +20-40% 加速 | 未实现 | 若端侧实现动态树，接受长度可接近 EAGLE-2 的 ~4.65 |
| 无需独立 draft model（self-speculative） | 端侧 Qwen 0.5B 是独立小模型 | EAGLE-2 的自投机路线在端侧更显存友好——不需要加载第二个模型 |
| 4.26× 加速 (Vicuna 13B)、3.05-4.26× (6 任务) | 本实验减速 4.7× | **对比极端**——论文在云端高端 GPU 上以更大模型差获得高加速比 |
| EAGLE-2 无需额外训练 | draft model 未训练 | 若在端侧训练 EAGLE-style draft head（target 前几层 + 轻量 head），显存远小于独立 draft model |

**核心对照**：EAGLE-2 的 **self-speculative 路线**可能是端侧投机推理的最优解——因为它不需要加载独立的第二个模型。在当前实验中，3.9 GiB 的双模型显存需求（vs 单独 2.98 GiB）是 c 值恶化的重要原因之一。EAGLE-2 的方案——利用 target model 自身的 hidden states 做 draft——在端侧 6GB 显存下可节省约 1GB（省去独立的 draft model）。

**与 myDraft_Verify 的关联**：`core/draft.py` 中的 `_draft_dynamic()` 方法实现了 EAGLE-2 的 confidence-driven 动态树。`models/loader.py` 中的 `extract_target_context()` 方法可提取 target model 中间层 hidden states——这是 DFlash KV Injection 和 self-speculative early exit 的基础设施。

### 8.4 DFlash (ICML 2026) — 块并行扩散 Draft

| 论文内容 | 本实验对应 | 对照结果 |
|----------|-----------|----------|
| Block diffusion 并行 draft：一次生成 16 tokens | vLLM 投机推理仅 k=3 线性 | DFlash 的并行 draft 理念是本报告"端侧异构并行"的理论支柱 |
| T_draft = t_parallel（常数）vs AR T_draft = γ × t_step | 端侧测得 t_step ≈ 17.9ms | 若 draft 可并行化（γ×t_step → t_parallel），c 值可从 0.43 降到接近 0 |
| KV Injection：每层 draft layer 注入 target features | `models/loader.py` `extract_target_context()` | 已提供基础接口，供自主实践使用 |
| 6.08× 加速 (Qwen3-8B), 2.5× vs EAGLE-3 | 本实验减速 4.7× | 对比再次印证：**并行 draft 是突破端侧瓶颈的终极方向** |
| 训练需要 800K+ 样本 + H200 GPU | 端侧无法训练 | 更多关注其设计哲学——"扩散 draft + 自回归 verify"的范式转移 |

**核心对照**：DFlash 的核心公式 `T_draft = t_parallel` （常数，不随 γ 增长）直接解决了本实验的核心问题——draft 阶段的串行性（γ 步 × t_step）使 c 值被放大。如果端侧能实现 pipeline 并行（在 verify 阶段同时执行下一轮 draft），理论上将 c 从 0.43 降到接近 0，投机推理恢复加速。

**这正是方向一研究报告提出"端侧异构并行"方案的理论基础**——将 draft model 的执行卸载到 AICPU/NPU 协处理器，在大模型验证的同时并行生成下一轮 draft tokens。本实验的 c=0.43 数据为这一方案提供了直接的量化依据。

### 8.6 论文驱动的后续方向

基于四篇论文分析，端侧投机推理（RTX 4050 6GB）有三条可行的优化路径：

| 路径 | 论文来源 | 具体方案 | 预期效果 |
|------|----------|----------|----------|
